# pptx 技能调整建议

> 依据：2026-08-24 用该技能完成「小安下半年建设材料.pptx → 长安汽车统一模板」全流程（读取、格式分析、裁剪生成、视觉验证）的实际体验。每条建议均附本次任务中的真实佐证。

## 结论摘要

技能的两个脚本（reader/updater）本身执行快、保真好，核心短板有三个：

1. **文本替换能力在 run 边界处断裂**——最常见的"改标题"场景反而做不到，只能绕开技能自己写脚本；
2. **设计层信息（母版/布局）是黑盒**——凡涉及"格式长什么样"的分析（页头、logo、封面封底）都必须离开技能另写 python-pptx 脚本；
3. **离开脚本后没有环境出口**——自写脚本时无从复用技能环境，导致依赖重复安装（本次执行时间偏长的主因之一）。

---

## P0：直接影响能力，建议优先改

### 1. 新增 `set_text` 操作：形状级整框替换（保样式，支持跨 run）

**问题**：`replace_text` 只在单 run 内查找。本次封面主标题"小安助手产品下半年建设规划"被拆成 `小安助手` + `产品下半年建设规划` 两个 run，JSON 指令完全无法命中；副标题"变革与效率部 | 2026.08.10 | 180天"被拆成 9 个 run。改标题/改副标题是增量编辑最高频的需求，却是最先失效的场景。

**建议**：新增操作，按形状定位后整框替换——保留第 1 个 run 的 rPr 样式写入新文本，删除多余 run 与多余段落（本次用 python-pptx 手工实现了这个逻辑，效果完美，可直接移植）：

```json
{ "type": "set_text", "slide": 1, "name": "文本框 2", "text": "新主标题" }
```

配套文档口径：`set_text` 适用于"换标题/换整个文本框内容"；`replace_text` 适用于"段落内局部改词"。

### 2. JSON 输出增加 `shape_id`，指令支持按 id 定位

**问题**：形状名不唯一。本次目录页 `文本框 486` 出现 4 次、`Lorem Ipsum` 出现 2 次，`delete_shape`/`replace_text` 按 name 匹配会产生误删/误改；而 reader 的 JSON 恰恰没有输出 shape_id，AI 拿不到唯一定位手段。

**建议**：
- JSON 每个形状增加 `shape_id`（python-pptx 的 `shape.shape_id`）；
- `delete_shape`、`set_text`、`move_shape` 等操作支持 `"id": 123` 定位（优先级高于 name）；
- SKILL.md 明确"同名形状歧义时用 id"。

### 3. reader 输出母版/布局形状明细与 slide→layout 映射

**问题**：技能定位是"保留模板与设计风格"，但页头横幅、logo、封面装饰线、封底元素全部位于**布局层**，design 摘要只有一行布局名列表。本次为搞清"页头格式来自哪一层"，必须自写脚本遍历 master/layout 形状（位置、尺寸、类型）。

**建议**：design 部分增加两个小节（文本量可控，每个布局通常只有 2~4 个形状）：

```
## Design
- Slide size / layouts / theme（现有内容保留）

### Layout shapes
- 4_封面: [图片1 PICTURE (21.98,15.32) 9.32x2.13] [图片3 PICTURE (7.70,3.44) 16.52x0.51] ...
- 仅标题: [图片2 PICTURE (0,0) 31.92x17.96]   ← 全幅背景图=页头视觉来源
- 封底: [图片17 PICTURE (10.82,8.23) 10.28x2.35] ...

### Slide -> layout
1:4_封面  2-21:仅标题  22:封底  23-34:仅标题
```

这一项做完，"分析模板格式"类任务（本次用户需求的原型）就能全程留在技能内完成。

## P1：效率与易用性

### 4. 增加"自写脚本如何复用技能环境"的指引

**问题**：SKILL.md 只定义了两个脚本入口。一旦任务超出指令能力（本次的跨 run 替换、布局遍历），AI 只能自写 python 脚本；文档没有告知如何复用技能已初始化的 venv，导致 AI 用 `uv run --with python-pptx` 另建环境、重新下载 lxml 等依赖（3.8MB+），既慢又浪费。

**建议**：在 SKILL.md 增加一节「自写脚本（逃生舱口）」：

> 需要超出 JSON 指令能力的操作时，优先复用技能环境运行自定义脚本：
> `uv run --project <skill_dir> python your_script.py`（依赖已锁定，不触发下载）。
> 自定义脚本仍应遵守：修改类操作输出到新文件，不覆写源文件。

（或者更彻底：提供 `scripts/pptx-python` 包装器，隐藏环境细节。）

### 5. 批量删页 / 保留式删页

**问题**：本次从 34 页裁到 5 页，需写 29 条 `delete_slide`。做"模板抽取""去附录"这类任务时指令膨胀严重。

**建议**：二选一即可：
- `delete_slide` 的 `slide` 接受数组：`{ "type": "delete_slide", "slide": [3,4,5,6,7,8,9,11,...] }`；
- 或新增 `{ "type": "keep_slides", "slides": [1,2,10,21,22] }`。

### 6. 补全 JSON 字段文档

**问题**：JSON 实际含有 `left_cm/top_cm/width_cm/height_cm`（本次靠自行探索发现），SKILL.md 未提及；run 样式中 `size: null` 表示"继承占位符/母版样式"这一语义也未说明，AI 容易误判为"无字号"。

**建议**：SKILL.md 的 JSON 说明补两句：① 形状含位置尺寸字段（cm）；② run 的 size/color/font 为 null 时表示继承自占位符/母版，分析实际显示值需结合布局层。

## P2：可选增强

### 7. 新增 `pptx-export-png`：结果视觉校验出口

本次用 PowerPoint COM 导出各页 PNG 并做视觉核对，是"格式保真"类任务里最有价值的一步（发现了大量仅靠文本无法确认的信息：密级标识、标语、logo 位置、无残留）。建议提供：

```
scripts/pptx-export-png <pptx> <outdir> [--width 1600]
```

实现优先走 PowerPoint COM（Windows 有 Office 时的保真度最高），无 Office 再降级 LibreOffice `soffice --convert-to png`。SKILL.md 注明"生成/大改后建议导图核对"。

### 8. 占位符样式继承的实际值解析

`size: null` 时若能顺手解析占位符→母版继承链，输出 effective size（如 `size: null (effective 20pt from layout)`），AI 判断格式规范（如"页头标题统一 20pt"）就不需要再查母版。锦上添花，优先级最低。

## 优先级与收益总览

| # | 建议 | 级别 | 解决的真实场景 |
|---|------|------|----------------|
| 1 | `set_text` 形状级替换 | P0 | 跨 run 的标题/副标题替换（本次被迫手写脚本） |
| 2 | JSON 增加 shape_id + 按 id 定位 | P0 | 同名形状的精确增删改（本次目录页 4 个同名文本框） |
| 3 | 布局形状明细 + slide→layout 映射 | P0 | 页头/封面/封底格式分析（本次被迫手写脚本） |
| 4 | 自写脚本环境复用指引 | P1 | 避免重复装依赖（本次执行时间偏长主因之一） |
| 5 | 批量/保留式删页 | P1 | 模板抽取、去附录（本次 29 条删页指令） |
| 6 | JSON 字段文档补全 | P1 | 位置字段、null 样式语义 |
| 7 | 导出 PNG 校验出口 | P2 | 生成结果的视觉保真核对 |
| 8 | 继承样式实际值解析 | P2 | 格式规范的自动归纳 |

P0 三项落地后，本次「抽取模板」任务可全程用 reader + updater JSON 指令完成，无需任何自写脚本；P1-4 落地后，超出指令能力的任务也不再重复初始化环境。
