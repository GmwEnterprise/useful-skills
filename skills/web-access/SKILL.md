# web-access —— opencli 哲学化信息获取

把「像人一样思考」的目标驱动调度哲学（目标驱动、过程校验、并行分治、站点经验积累）落到 opencli 执行层：适配器结构化优先，`browser` 兜底复杂交互。

## 核心原则：像人一样思考（目标驱动，非步骤驱动）

整个过程遵循四步循环：

1. **拿到请求 → 明确成功标准**：什么算「完成」？需要哪些字段、哪些来源、多高可信度？
2. **选择起点 → 选最可能直达的方式作为第一步验证**：而不是按固定顺序把所有通道走一遍。
3. **过程校验 → 每步结果都是证据而非二元信号**：对照成功标准更新判断；方向错了立即调整，**不在同一方式上反复重试**。搜索没命中不等于「还没找对方法」，也可能是「目标不存在」。
4. **完成判断 → 对照标准确认完成，不过度操作**。

## 信息真实性原则（一手优于二手）

**一手信息优于二手信息。** 搜索引擎和聚合平台只是**发现入口**，定位到候选后必须跳到一手来源（官网、官方平台、原文）确认。

**拒绝 AI 摘要源**：禁用 `opencli grok/doubao/gemini` 等 AI 适配器（返回模型生成的综述，属失真的二次信息）。

| 信息类型 | 一手来源 |
|----------|---------|
| 政策 / 法规 | 发布机构官网 |
| 企业公告 | 公司官方新闻页 |
| 学术声明 | 原始论文 / 机构官网 |
| 工具能力 / 用法 | 官方文档 / 源码 |

找不到官网时，权威媒体的原创报道（非转载）可作次级依据，但需向用户声明转述误差可能。

## opencli 基本操作

### 命令语法与 strategy

统一入口 `opencli <site> <command> [args] [options]`。每个适配器命令带一个 `strategy` 标签，决定是否需要浏览器：

| strategy | 需 Chrome | 含义 |
|---|---|---|
| `PUBLIC` | 否 | 纯 HTTP，无需登录 |
| `LOCAL` | 否 | 本地 / 开发端点 |
| `COOKIE` | 是 | 复用浏览器登录态 cookie |
| `INTERCEPT` | 是 | 自动开窗捕获带签名的请求 |
| `UI` | 是 | 完整 DOM 交互 |

`COOKIE` / `INTERCEPT` / `UI` 需 Chrome 已登录目标站 + 已装 opencli 扩展；命令直接复用当前会话凭证，无需重新登录。

### 通用 flag

| flag | 作用 |
|---|---|
| `-f, --format <fmt>` | `table`（TTY 默认）/ `yaml`（非 TTY 默认）/ `json` / `plain` / `md` / `csv`。Agent 优先 `yaml` 或 `json` 拿结构化输出 |
| `-v, --verbose` | 调试日志 + 失败堆栈 |

命令专属 flag（`--limit`、`--tab`、`--filter` 等）非通用，以 `<site> <command> -h` 为准。

### 发现与预检

每次使用前必须先做（不计入搜索次数）：

- `opencli list -f yaml` —— 用 live registry 确认候选站点是否存在，检查 `strategy`、`browser`、`domain`
- 选定站点后：`opencli <site> -h` —— 查看该站点有哪些子命令
- 锁定子命令后：`opencli <site> <command> -h` —— 查看参数、输出列、策略

**例外**：URL 已知的公开页直接读（L2 `opencli web read`），无需完整预检，但仍以 `opencli web read -h` 的实际参数为准。

**禁止**在文档里硬编码命令签名或假设参数；一律以 `-h` 实时输出为准，避免文档漂移。

### 排障

`COOKIE` / `INTERCEPT` / `UI` 适配器或 `opencli browser *` 失败时，先跑 `opencli doctor` 诊断浏览器桥（daemon + 扩展 + Chrome 连接）。`PUBLIC` / `LOCAL` 适配器和 `opencli list` 不依赖浏览器桥，无需 doctor 绿。

## 通道分层（L1-L4）

按目标特征选通道，优先选最可能直达的层：

| 层 | 用途 | opencli 实现 |
|----|------|--------------|
| **L1 公开发现** | 搜索 / 关键词定位 | **`opencli google search`（默认首选）**；google 不可用 / 被墙 / 结果不足时用 `duckduckgo`、`brave` 等兜底（`opencli list` 查可用搜索引擎） |
| **L2 公开抓取（快路径）** | URL 已知的公开页（项目信息 / API 文档 / 公开资料） | `opencli web read`（输出 Markdown 正文，最适合取主内容） |
| **L3 登录态结构化站点** | 有适配器的站点 | **`opencli <site> <command>`（首选，columns 后端清洗，结构化 JSON）** |
| **L4 浏览器兜底** | 无适配器 / 适配器不全 / 复杂交互 | `opencli browser *`（open/click/type/extract/network/screenshot，复用 browser bridge，无需自建 proxy） |

### 通道选择决策

1. 用户明确指定网站/平台 → 该站点有适配器走 **L3**；无适配器走 **L4**
2. 用户未指定网站 → 先 **L1**（搜索定位，默认 google）；定位到具体站点后：
   - 该站点有适配器 → **L3**（结构化 JSON，最省 token）
   - 该站点无适配器但有公开页 → **L2**
   - 需要登录态或复杂交互 → **L4**
3. URL 已知的公开页（项目信息 / API 文档 / 公开资料等）→ **直接 L2**，跳过完整预检，快速取主内容

> **L3 永远优先于 L4**：裸 CDP `/eval` 抓取的原始 HTML 比纯文本可多消耗上百倍 token，且清洗责任全压在 AI 手写 JS 上，稳健性差。

> **常见登录态社交平台大多已有适配器**：小红书、微博、知乎、B站、贴吧、虎扑、抖音，X / Twitter、Instagram、Reddit、TikTok 等。这类站点先用 `opencli list` 确认适配器存在。

### L4 浏览器执行

L4 的具体操作（`opencli browser` 的 open / click / type / extract / network / screenshot / scroll 用法、选择器优先契约、stale-ref 处理、网络捕获）**加载 `opencli-browser` skill 获取**，不在本文重复。

- 媒体：图片用 `extract` 取 URL 后定向读取；视频用 `screenshot` 对当前帧采样（真实渲染）
- 环境整洁：用完自己创建的 tab 即时关闭，不操作用户已有 tab
- 风险：部分站点对浏览器自动化检测严格，存在账号风险；L4 仅在 L3 无适配器或拿不全字段时使用

## 程序化 vs GUI 交互权衡

- **程序化**（L1-L3，构造 URL、调适配器命令）：快、精确、省 token，但易触发反爬
- **GUI 交互**（L4，`opencli browser` 点击/填表/滚动）：慢，但最像人、确定性最高

**GUI 是程序化的有效探测**：通过真实交互观察站点行为（URL 模式、必需参数、跳转逻辑），为程序化提供依据；程序化受阻时 GUI 是可靠兜底。

### 站点内交互链接可靠性

> 站点内交互产生的链接**可靠**（携带平台所需完整上下文，如小红书 `xsec_token`）；手动构造的 URL 可能缺隐式参数。

实践：优先用适配器返回的 `url` 字段作为下一步入口，而非自己拼 URL。

## 登录判断

核心问题只有一个：**目标内容拿到了吗？**

1. 先尝试用适配器命令（L3）或公开抓取（L2）获取内容
2. 只有确认拿不到、且判断「登录能解决」时，才请用户登录
3. COOKIE / INTERCEPT / UI 策略适配器复用浏览器登录态，无需额外处理
4. 登录完成后**无需重启**，直接刷新继续

不要一上来就要求登录。先试，拿不到再判断。

## 并行分治

当存在**多个独立目标**时，派子 Agent 并行处理，主 Agent 只收摘要。

**分治判断**（同时满足才分）：

- 目标彼此独立
- 量足够大 / 需长任务
- 简单单页不分

**子 Agent prompt 规范**：

- **目标导向措辞**：用「获取 / 了解 / 调研 / 找到」，**避免**暗示执行手段的动词（"搜索"会锚定 L1 搜索引擎，而反爬站点可能需 L3 / L4 直达）
- **必须写明**：「加载 web-access skill 并遵循其指引」
- 主 Agent 只收摘要，**脏数据 / 原始抓取不进主上下文**（上下文保护）

子 Agent 各自调 opencli，但 **opencli 并非无竞态**——并行需满足以下前提：

- **跨站点并行安全，同站点并行危险**：不同目标站点可放心并行；同一站点的多次请求必须串行 + 退避，否则触发反爬（429 / 封号），opencli 不在 adapter 层替你控并发
- **L4 browser 并行需不同 session 名**：每个子 Agent 用各自的 session（如 `opencli browser probe-a ...`、`probe-b ...`），否则抢占同一 tab lease
- **共享单 Chrome**：全局只有一个 daemon + 一个 Chrome，所有 `browser:true` 适配器（COOKIE / INTERCEPT / UI）和 L4 命令都经它；`browser:false`（PUBLIC）适配器走 Node fetch，不占 Chrome，可自由并行
- **节奏**：N 个子 Agent 跨 N 个不同站点并行收益最大；同站多查请留在单子 Agent 内串行

## 技术事实（DOM / 反爬）

处理 L4 浏览器兜底时需知：

- 页面有大量已加载未展示内容（轮播非当前帧、折叠区、懒加载占位），以数据结构为单位可直接触达
- DOM 有选择器不可跨越的边界（Shadow DOM `shadowRoot`、iframe `contentDocument`），需递归遍历
- `/scroll` 到底触发懒加载
- 平台「内容不存在」「页面不见了」提示**不一定反映真实状态**，可能是访问方式问题（URL 缺参、触发反爬）
- 短时间密集打开页面会触发反爬风控 → 控制节奏

## 站点经验积累

按**主域名**存经验到 `refs/site-patterns/{domain}.md`，格式见 `refs/site-patterns/_template.md`。

**域名归并**：`{domain}` 用主域名（apex / eTLD+1，不含子域名前缀）。opencli 各命令的 `domain` 字段常含子域名（如 12306 命令有 `12306.cn` 也有 `kyfw.12306.cn`），一律归并到主域名文件（`12306.cn.md`），子域名记入 frontmatter `aliases`，不单建文件。

记录字段：`domain` / `aliases` / `updated` frontmatter + 平台特征 / 适配器命令（含已知坑）/ 有效模式 / 已知陷阱（含发现日期）。

**原则**：

- 当作「可能有效的提示」而非「保证正确」
- 按经验失败则回退通用模式并更新文件
- 操作成功后**主动写入验证过的事实**，不写未确认猜测

## 单题预算与频率限制

「单个用户问题」= 同一意图链路下的一次求解；追问/澄清若核心问题未变，仍算同一题。

**先建台账**，每次真正执行搜索命令后立即更新：`site` / `query` / `count` / `status`。

**计数规则**：

- `opencli list`、`opencli <site> -h`、`<command> -h` 属预检，**不计**
- 一次真正的 `opencli <site> ...` 执行 = 该站 1 次
- 因报错 / 超时 / 验证码 / 反爬 / 登录态异常失败，**也算 1 次**，不无限重试

**频率上限**：

- 每个站点默认最多 **2 次**；第 2 次必须有明确理由（加时间 / 地区 / 类别 / 关键词限定）
- **不进行第 3 次**；信息仍不足时，停止扩搜并明确说明缺口

**触发限频后**：记录「已跳过：<site> 达到频率上限」→ 改用同类站点 → 无替代则基于已收集信息回答并说明缺口。

## 处理不可用的源

- 不要因为单个源失败而中止整个搜索
- 记录：「已跳过：<site> 不可用」
- 回退到同类其他站点，或回退到通用搜索引擎（L1）
- 始终以 `opencli list -f yaml` 与 `opencli <site> -h` 的实际结果为准

不要假设任何站点「绝对可用」。

## 查询结束汇报

每次查询末尾追加「搜索摘要」：

```md
搜索摘要
- 网站：<site1> | 查询词：<term1> | 次数：<n>
- 网站：<site2> | 查询词：<term2>；<term3> | 次数：<n>
- 已跳过：<site3>，原因：达到频率上限
```

## 范围说明

本技能聚焦**读类调研**（搜索 / 抓取 / 核实 / 调研）。发布、评论、点赞等**写操作不在范围内**；登录仅用于读取登录态内容。

> opencli 无「本地书签 / 历史检索」能力（web-access 原有的 `find-url` 能力）。若需定位「之前看过的页面」「公司内部系统」等公网搜不到的目标，需另行配备本地检索工具。
